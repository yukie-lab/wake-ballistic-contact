# シミュレータ v1 性能実測記録(出口条件: 60 fps 目標)

計測: 2026-08-16 / M4 iMac / Chrome / devicePixelRatio=2 / キャンバス 1674×752 css px
方法: 各描画関数を明示ループ 60 回で実測(ms/フレーム)。rAF 依存の fps 計は
ウィンドウのオクルージョンで停止するため、フレームコスト直測を一次記録とする。
(CDP 経由: `WAKE.timeline.draw()` / `WAKE.space.frame()` / `WAKE.map.draw(true)`)

| 対象 | ms/フレーム | 備考 |
|---|---|---|
| 航跡タイムライン | 0.66–0.88 | 2,197 エントリ・CI90 リボン(色×透明度グループの一括ストローク) |
| フライバイ網 3D | 0.46–0.53 | 誤差束 32 本/星(≈70k 頂点)・毎フレーム線形伝播更新込み |
| 排除地図(強制再描画) | 4.99 | スライダー操作時のみ。240×160 セル ImageData 生成 |
| 排除地図(通常フレーム) | ≈0 | 入力キー差分で再描画スキップ |

60 fps 予算 16.7 ms に対し全ビューで余裕 3〜30 倍。実表示 fps は vsync 上限に
張り付く(画面右下の常時 fps 計で確認可能。ウィンドウが隠れていると rAF が
停止し 0–数 fps 表示になるが、これはオクルージョンでありシミュレータの性能
ではない)。

## 高速化の経緯(v1 初版 → 本版)

初版はタイムライン/3D 実測 3–6 fps(オクルージョン込み計測だったが、コスト
自体も過大)。原因と対処:

1. **毎フレームの canvas 再確保**: `cv.width = …` を無条件代入(2D)、
   `renderer.setSize` を毎フレーム呼び出し(WebGL — `setPixelRatio` 未設定で
   サイズ比較が常に不一致)。→ サイズ変更時のみ再確保。
2. **エントリ個別のパス描画**(2,197×3 回の stroke)→ 色×透明度でグループ化
   した Path2D 一括描画(グループ数 ~8)。
3. **地図ヒートのセル毎 fillRect**(~26 万回/フレーム)→ 240×160 ImageData を
   オフスクリーン生成して拡大転写+入力キー差分での再描画スキップ。

## 束本数の確定(実装指示書 裁定1)

「まず 16 で組み、余裕があれば 32」— 16 本時の実測(3D 0.53 ms/フレーム)で
余裕 30 倍を確認し、**32 本に増量して確定**(32 本時 0.46 ms — 頂点数は倍増
だが毎フレーム CPU 更新は同オーダーで、差は計測ゆらぎ内)。カタログ v1.1 の
display_bundle は 32 サロゲート(実共分散・裁定#18 裁定1)。
